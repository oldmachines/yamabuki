SA-1: Teaching Old Games a Second CPU

How yamabuki rewrites 1990s Super Nintendo games to use a coprocessor they were never written for

This talk is about a chip called the SA-1, a second processor that Nintendo put inside some Super Nintendo cartridges, and about a program called yamabuki that takes games written years before that chip existed and rewrites them, mechanically, so that they use it.

I am going to assume you know nothing about the Super Nintendo. Every part name, every register, every piece of jargon gets explained the first time it appears. If you already know the machine, the first part will be quick.

Part one

The Super Nintendo, for people who never opened one

Part one. Before the coprocessor makes any sense, we need a picture of the machine it plugs into. This is a 1990 games console, and almost every decision in the rest of the talk traces back to one of its constraints.

What's in the box

Five parts, and one wire between them. The bus is a shared set of address and data lines: one chip at a time puts an address on it and everyone else answers or ignores it.

⟨CLICK⟩

The S-CPU is the main processor. Its core is a 65816, a sixteen-bit descendant of the 6502 in the Apple II and the NES. It runs at three point five eight megahertz at best. Every instruction of the game, every enemy's decision, every score update, executes here. It is also the only chip that can read the controller.

⟨CLICK⟩

WRAM, work RAM, is 128 kilobytes of ordinary memory. Every variable the game has lives here: where the player is, how much health, which enemies are alive, the stack the CPU uses for subroutine calls. Remember this box. The whole talk is about who can reach it.

⟨CLICK⟩

The PPU is the picture processing unit. It draws the screen out of tiles and sprites from its own private memories: VRAM for graphics, OAM for sprite positions, CGRAM for colours. The CPU cannot address those directly. It writes to them through hardware registers.

⟨CLICK⟩

The APU is the audio unit, and it is really a second, separate computer with its own tiny CPU and 64 kilobytes of its own memory. The main CPU can only talk to it through four one-byte ports, with a handshake protocol the game code has to follow byte by byte.

⟨CLICK⟩

And the cartridge. It carries the ROM, the game's code and data, read-only. But the slot exposes the whole bus, which means a cartridge can carry anything: extra RAM, a battery, or an entire second processor. That is the door the SA-1 walks in through.

Sixty times a second

The television dictates the rhythm. Watch the screen: a beam paints the picture one horizontal line at a time, top to bottom, and then flies back up to start again, sixty times every second.

⟨CLICK⟩

There are 224 visible lines. While they are being painted, the video chip, the PPU, is reading its memories continuously, and the CPU may not touch them.

⟨CLICK⟩

Then the beam flies back to the top. That gap is the vertical blank, or vblank. The lamp on the set lights up while it lasts. Nothing is being drawn, so for that short moment video memory is free.

⟨CLICK⟩

The hardware announces the start of vblank by firing an interrupt, the NMI. Non-maskable means the CPU cannot refuse it: whatever it was doing, it jumps to a routine the game installed, the NMI handler. And this is the only moment the CPU can upload the next frame's sprites, tiles and colours to the PPU. Watch the arrow: it only lights while the lamp is on.

⟨CLICK⟩

Because the frame is exactly one sixtieth of a second and the CPU's clock never changes, every frame is the same number of CPU cycles: mostly painting time, a sliver of vblank. That fixed budget is the thing that will matter.

⟨CLICK⟩

And here is the habit of the era: most games do everything in that handler. Read the pad, move everything, resolve collisions, upload graphics, return. The NMI is not just an interrupt, it is the game's main loop. Gradius III, our first target, is exactly like this.

Where everything lives: the address map

The 65816 addresses sixteen megabytes with a 24-bit address, which everyone writes as a bank byte, a colon, and a sixteen-bit offset. Bank 7E, offset 1E0A.

⟨CLICK⟩

The first sixty-four banks are the system banks and they all look alike. The top half of each is a 32 kilobyte slice of the cartridge ROM, which is how a 512 kilobyte game spreads across many banks.

⟨CLICK⟩

In the middle sit the hardware registers, MMIO, memory-mapped input and output. Writing to address 2118 does not store a byte anywhere; it sends a word to the PPU. Reading 4218 gives you the controller buttons. These are not memory, and that distinction will come back with a vengeance.

⟨CLICK⟩

The bottom eight kilobytes of every system bank is a mirror of the first eight kilobytes of WRAM. Games love it, because short two-byte addresses are faster than long three-byte ones. So the hottest variables of every SNES game live in this low mirror.

⟨CLICK⟩

Banks 7E and 7F are the full 128 kilobytes of WRAM, addressed the long way. And the low mirror and the start of 7E are the same physical bytes, reachable by two different names.

⟨CLICK⟩

That double naming is the first real problem for a rewriter. If you move WRAM, you must find every instruction that names it, whichever of the two names it used, and there is a third name, through a register, coming on the next slide.

Four things about the processor, and they all come back later.

⟨CLICK⟩

It has one accumulator, A, where arithmetic happens, and two index registers, X and Y, mostly used as offsets into tables.

⟨CLICK⟩

The direct page register, D, is a base address. When the code says load from address five, it means D plus five. Games set D once at boot, usually to zero, so direct-page addresses land in the low mirror. If a rewriter moves the low mirror, it can move D instead of rewriting thousands of instructions. Hold that thought.

⟨CLICK⟩

The data bank register, DBR, is the bank byte the processor silently glues onto every sixteen-bit address. Load from 1E0A actually reads DBR colon 1E0A. So what an instruction touches depends on a register that was set somewhere else, maybe hundreds of instructions earlier.

⟨CLICK⟩

And the width flags. The accumulator and the index registers can each be eight or sixteen bits wide, switched at run time. On the right: the bytes A9 7E are a complete instruction in eight-bit mode, and only two thirds of one in sixteen-bit mode. The length of the instruction depends on a flag set at run time. So you cannot reliably disassemble 65816 code by reading the bytes. You have to run it, or know exactly what ran. That is why an emulator sits at the centre of this whole pipeline.

Five ways to name a byte

These are the addressing modes the rewriter will have to reason about. Each one hides a different amount of information.

⟨CLICK⟩

Direct page: two bytes, fast, adds D. Games keep their hottest variables here.

⟨CLICK⟩

Absolute: a sixteen-bit address, with the bank supplied by the DBR register. The instruction alone does not tell you whether it reads RAM or ROM.

⟨CLICK⟩

Long: the full 24-bit address, bank included. This is the only mode where the bytes of the instruction say exactly which memory is touched.

⟨CLICK⟩

Indexed: a base plus X. And this is the nasty one. The base can be zero and X can be anything, so LDA zero comma X is the game's way of saying "X is a pointer, read what it points at". Same instruction, one time walking a table in ROM, the next time walking a list in RAM. The bytes do not know.

⟨CLICK⟩

Indirect: the address itself is stored in memory as data. A rewriter that only looks at instructions never sees it.

⟨CLICK⟩

So of five ways to name a byte, only one is honest about which byte. The others depend on registers or on data. Keep this in mind when we get to "structure versus values".

Slowdown: when the frame doesn't fit

Now the constraint that started all of this. Each box is one frame, one sixtieth of a second, one fixed budget of cycles. The gold bar is how much of it the game's logic used. On a quiet screen with a few enemies, it fits with room to spare, and the CPU spends the rest of the frame waiting for the next vblank.

Box = frame budget; gold = work; rest = waiting

Slowdown: when the frame doesn't fit

Twenty enemies on screen, bullets everywhere. The same logic now takes longer than one frame. The next NMI arrives while the handler is still running, the game notices, drops that frame, and the picture repeats. The player sees the game slow to half speed, a third, a quarter. Gradius III is famous for it. This is the thing the SA-1 conversion removes, and the fact that it removes it, changing how many frames the game executes, is exactly what makes the result so hard to verify later.

Why 1990 games were slow

  • The 65816 runs at 3.58 MHz — and only when reading fast ROM chips. Cheaper cartridges force it down to 2.68 MHz ("SlowROM").
  • Games kept growing: more sprites, more physics, bigger levels. The CPU did not.
  • The CPU burns exactly the same cycles every frame. The only question is how many of them it spends waiting.

Why was this so common? Three reasons.

⟨CLICK⟩

The processor is slow, three and a half megahertz at best, and most early cartridges used cheaper, slower ROM chips that throttled it to two point six eight. Yamabuki's first rung, a FastROM patch, only fixes that second part.

⟨CLICK⟩

And the games kept growing. A 1994 game asked far more of the same chip than a 1991 game did.

⟨CLICK⟩

The last bullet is a way of thinking that the profiler is built on. The CPU never speeds up or slows down. Every frame it executes the same number of cycles. A fast game is one that spends most of them waiting; a slow game is one that never gets to wait. So when we ask "how busy is this game", we are really asking "how much did it wait". That is literally how yamabuki measures it.

Part two

The SA-1: a second computer inside the cartridge

Part two: the chip itself. What it is, what it can see, and, just as important, what it cannot.

Nintendo's answer, 1995

  • A second 65816 — the same instruction set as the console's own CPU — running at 10.74 MHz, three times faster
  • Soldered inside the cartridge, so the console never changed. Super Mario RPG, Kirby Super Star, Kirby's Dream Land 3 shipped with one.
  • It was designed for games written for it. Nobody planned for retrofitting a 1990 game.

By 1995 the console was five years old and visibly struggling. Nintendo's fix, for its own biggest titles, was the SA-1.

⟨CLICK⟩

It is a second 65816, the same instruction set as the S-CPU, so the same programmers could write for it, but clocked at ten point seven four megahertz, three times the console's.

⟨CLICK⟩

It sits inside the cartridge. That is the trick of the whole era: the console is fixed, but the cartridge slot exposes the bus, so you can put whatever you like on the other side of it. Super Mario RPG and the Kirby games are the famous ones.

⟨CLICK⟩

Those games were built around the chip from day one. What we are going to do, taking a game written before the chip existed and making it use one, was never the plan. A hacker named Vitor Vilela proved it could be done by hand. Yamabuki tries to do it by machine.

The CPU is not the whole chip

The chip is more than a processor, and it is worth seeing the whole thing once, if only to notice how little of it the conversion needs.

⟨CLICK⟩

The core: a 65816 with its own registers and its own stack. Two processors, running at the same time, on the same cartridge.

⟨CLICK⟩

The Super MMC is a bank switcher. It maps one-megabyte regions of a large ROM into the address space, four at a time. For a small game it just mirrors; for a three-megabyte game like Super Metroid it becomes a real problem, and we will meet it in part ten.

⟨CLICK⟩

A DMA engine for bulk copies, and a character-conversion unit that turns plain bitmaps into the tile format the PPU wants. Super Mario RPG used that for its rotating sprites.

⟨CLICK⟩

A hardware multiplier and divider, faster than anything the CPU can do in software.

⟨CLICK⟩

Timers, and interrupt lines in both directions, so each processor can poke the other.

⟨CLICK⟩

And its memories, which get the next slide to themselves.

⟨CLICK⟩

Four memories — three of them shared

Two processors, four memories. Which processor can reach which is the whole design problem, so let's go one at a time.

⟨CLICK⟩

ROM: the game's code and data. Both processors can read it. Good.

⟨CLICK⟩

BW-RAM, battery-backed work RAM on the cartridge, up to a quarter of a megabyte. Both can read and write it. This is where the two processors can share state.

⟨CLICK⟩

I-RAM, two kilobytes inside the chip. Both can reach it, and for the SA-1 it is the fast page-zero memory. Small, but ideal for passing messages.

⟨CLICK⟩

And WRAM. The console's 128 kilobytes. Every variable the game has ever stored. The S-CPU sees it, of course.

⟨CLICK⟩

The SA-1 does not. It is not on the cartridge side of the bus, and there is no path. So the sentence "run this routine on the fast chip" is meaningless as written, because that routine's variables are all in a memory the fast chip cannot address. A conversion is never "move the code". It is "move the code and every byte of state it touches out of WRAM". That single fact drives everything from here on.

How 256 KiB fits through an 8 KiB hole

Here is how the console sees the cartridge's RAM, and it is a little strange.

⟨CLICK⟩

On the S-CPU side, every system bank has an eight kilobyte hole at 6000 to 7FFF, and BW-RAM shows through it. Only eight kilobytes at a time, because that is all the space the map has left. Notice the SA-1's registers sit just above the WRAM mirror, at 2200. That placement causes a spectacular bug later.

⟨CLICK⟩

BW-RAM itself is up to 32 blocks of eight kilobytes.

⟨CLICK⟩

Register 2224 chooses which block is showing in the hole. It is a sliding window.

⟨CLICK⟩

The SA-1 does not need the window. From bank 40 upward it addresses all of BW-RAM linearly. It also has a window of its own at 6000, chosen by register 2225. And where the console has its WRAM mirror at address zero, the SA-1 has its I-RAM.

⟨CLICK⟩

That asymmetry is the shape of every SA-1 design: the console works through a keyhole, the coprocessor works in the room. But if you point both windows at block zero, then address six-something means the same byte on both processors. Remember that sentence. It is the foundation the conversion stands on.

Saying anything: the mailbox

How do two processors that share a cartridge actually talk? Through a pair of message registers. The S-CPU writes four bits into register 2200 and can raise an interrupt on the SA-1 at the same time. The SA-1 answers through 2209, and can interrupt the console back.

Four bits is not a conversation. So anything real, the registers you want the other side to load, the direct-page base, the data bank, a frame counter, goes through I-RAM, which both can read. Yamabuki's generated code calls that shared area the mailbox. One side fills the cells, sends the message, and the other side picks them up.

One more capability, mentioned because it caused the first bug yamabuki ever hit with these conversions: the SA-1 can override the console's own interrupt vectors, the addresses the S-CPU jumps to on reset and on NMI. The hand-made patches boot the whole thing through that mechanism. An emulator that overlays those vectors on every read instead of only on a real vector fetch breaks every such patch at once. Yamabuki did that, for a while.

Vector override (SNV/SIV) — the first emulator bug

It computes. It cannot draw, sing, or read the pad.

  • The PPU, the APU, the controllers and the DMA registers are all MMIO in the console — on the S-CPU's side of the bus.
  • From the SA-1, those addresses are open bus: reads return garbage, writes vanish.
  • So a routine that touches a hardware register can never simply be moved. Every design has to separate compute (movable) from IO (stays home).
  • And timing: the PPU only accepts uploads during vblank. Whoever does IO must do it on the console's clock.

Now the limits, and they are hard limits.

⟨CLICK⟩

Everything the game does to the outside world, drawing, sound, reading the controller, copying graphics with DMA, happens by writing to hardware registers. Those registers live in the console.

⟨CLICK⟩

On the SA-1 those same addresses are open bus, a term for "nothing is connected here". A read gives you whatever was last on the wires, a write goes nowhere. There is no error. The code just silently does nothing, or reads nonsense and carries on.

⟨CLICK⟩

So when yamabuki looks at a routine and asks "can this run on the SA-1", the first question is "does it touch a register". In Gradius III, 628 routines were profiled and only 26 touch hardware. That is the good news: the game is ninety-six percent pure computation. The bad news is that those 26 are called from everywhere, and each call site is a boundary you have to engineer.

⟨CLICK⟩

And the IO is not just "where", it is "when". Video uploads must happen during vblank, on the console's clock. Whoever does IO has to be the processor that feels the frame.

Before we leave the hardware: this is the entire configuration of the shared memory. Four writes. Both windows on block zero, write permission on, no protected area.

Look at what the register set is telling you, though. Write enable is a separate register per processor, and there is a protected-area size on top. That is a designer saying: two processors will write the same bytes at the same time, and it will go wrong. Every concurrency bug in part eight is that warning coming true.

Two targets, deliberately different in shape.

Gradius III is the poster child for SNES slowdown. Its whole engine lives in the NMI handler, once per frame, and the ROM is small: half a megabyte, code in just two banks. That makes it the ideal first target.

Super Metroid is the hard one. It has a real main loop with a heavy interrupt on top, its state handling is far more indirect, and at three megabytes it is large enough that the SA-1's bank switcher can no longer pretend the address space is a simple mirror.

What they share is what every game of the era shares: all state in WRAM, timing everywhere taken for granted, and no notion that anything but the S-CPU would ever execute their code.

The hand-made precedent

Yamabuki: the emulator is the instrument

Yamabuki started life as a Super Nintendo emulator, written in Zig, fast enough for cheap ARM handhelds. The conversion tool is not a separate program bolted on. It is the same emulator, used as a measuring instrument.

⟨CLICK⟩

One core. The processors, the video chip, the sound chip, and the cartridge coprocessors including the SA-1, all cycle-accurate and deterministic.

⟨CLICK⟩

Compiled one way, it is the player: the desktop app and the libretro core. In the player, F10 records your controller inputs as a movie file, and those recordings are what feed the pipeline later.

⟨CLICK⟩

Compiled another way, it is the profiler. Every instruction that executes is recorded, with the width flags it ran under, and, crucially, for every data access, where it actually landed: ROM, the WRAM mirror, the long WRAM banks, or a hardware register. This is the knowledge a disassembler can never have.

⟨CLICK⟩

⟨CLICK⟩

⟨CLICK⟩

Part four

Step 1 — Is the CPU actually the problem?

Part four, the first rung that matters: measuring. Because a chip that triples your CPU speed is worthless if the CPU was not the bottleneck.

You cannot time the CPU. Measure the waiting.

The obvious approach fails. You cannot ask "how long did the CPU work this frame", because on a SNES the CPU burns exactly the same cycles every frame whether it was busy or idle. So yamabuki measures the complement: how long it spent waiting.

⟨CLICK⟩

What does waiting look like at the instruction level? Compare two loops. A checksum walks through memory: every pass touches new addresses. That is work.

⟨CLICK⟩

A wait loop reads the same one or two addresses over and over, is the vertical blank here yet, and branches back. Watching one spot for something else to change it is what waiting is.

⟨CLICK⟩

So the rule: a loop is a wait if it goes nowhere. Then the refinements, each forced by a real game that broke the naive version. A loop is recognised by where it returns to, not by nearby addresses, because Contra III's wait is a subroutine call inside a six-kilobyte loop. And pushes and pops don't count as side effects.

⟨CLICK⟩

The payoff of measuring it this way: idle time is headroom, and headroom is precisely the thing a faster processor would give you back. If a game has no idle time in its busy scenes, an SA-1 will help. If it has plenty, the slowdown is somewhere else.

Death 1: the marshalling toll

Why did the first design win nothing? Follow one call. The S-CPU copies the routine's working set, five kilobytes for the physics routine in Gradius III, into a shadow in BW-RAM. It sends "go". The SA-1 runs the routine against the shadow. It sends "done". The S-CPU copies five kilobytes back.

The copies alone cost as much as the routine did. And during the SA-1's run, the S-CPU is not doing anything else; it is spinning, waiting for "done". So the console paid to move the work, and then waited for it anyway. Correct, verified, and pointless. The lesson: the state must already be where the SA-1 can see it, with no copying, and ideally the console should not have to wait.

Death 3: the whole game on the SA-1

The third design is the one everyone thinks of first. Just run the whole game on the fast chip. When it touches a hardware register, forward the access through the mailbox to the S-CPU, which performs it and replies.

This was pushed a long way. Every rewriting problem it raised was solved: the direct page set-up, the pointer idioms, all of it. The game boots. It gets as far as the sound chip's boot handshake, which is: send a byte, wait for the echo, send the next. Each half of that is a forwarded transaction. After one point eight million of them the upload still is not finished, because every register access is now a round trip at the console's speed, and the game makes five hundred of them per frame.

The verdict is architectural. Synchronous forwarding of hardware access breaks the machine's timing contract: handshakes, fades, anything that assumes a register write is a few cycles. That is presumably why the hand-made patches keep the game on the S-CPU and move the data instead.

The SA-1 cannot address WRAM, and WRAM is where every variable of the game lives. Something has to give.

On a three-megabyte game, the SA-1's bank switcher parks the third megabyte in that upper region. The game's code was written for the console, where A0 was a mirror; under the SA-1's map it is real, different data. Every bank byte the code names now has to be translated.

⟨CLICK⟩

That translation is the de-mirror map, and it has to ride every carrier of a bank byte: instruction operands, immediates, the bodies of generated thunks, and values in data tables. Most of the Super Metroid bugs were exactly one of those carriers being missed: a thunk body that kept its original bank, a pointer table pinned through a push-and-pull, a sound-driver dispatch that swapped the bank into the low half of a sixteen-bit load with XBA.

⟨CLICK⟩

And the game's habits are harder throughout. Banks travel as data in a dozen idioms. Room loads decompress for eighty frames inside the interrupt. And there is a save game, so battery RAM has to move too, to bank 42 of BW-RAM, with its mirroring preserved for the boot-time probe.

What no CPU rewrite reaches: the DMA unit reads its own tables

Super Metroid's most instructive bug was one the whole CPU-side toolkit was blind to.

⟨CLICK⟩

HDMA is the console's per-scanline copier: a table in ROM says, for each group of lines, fetch these bytes from this address and write them to this register. One such table named a buffer in low WRAM.

⟨CLICK⟩

The DMA engine walks that table by itself. No instruction executes. So there is no operand to rewrite, no instruction to profile, no evidence bit. The entire pipeline is built on watching instructions, and here there is none.

⟨CLICK⟩

After relocation the buffer lives at 67EB, the game fills it correctly there, and the DMA engine fetches zeros from the abandoned 07EB. The Ceres escape rendered as a full-screen sheet of garbage tiles.

⟨CLICK⟩

Two fixes, both in the generator, neither in the game. First, a hook at the moment HDMA is armed records every such table, and the generator walks them and shifts low-WRAM addresses in the ROM itself. Second, the table's bank byte arrives as data through a register write, so that write gets a runtime thunk, the same shape as the DMA bank thunk from part six.

⟨CLICK⟩

And the lesson in bold: the behavioral verifier passed the whole time, because it compares game logic, never the picture. Behaviorally equivalent means the game plays correctly. It does not mean every pixel matches. The proof of the fix was the tiles appearing, and the confirming experiment was disabling that HDMA channel on the original game and watching it break the same way.

Glossary I — the machine

S-CPU
the console's 65816 processor, 3.58 MHz; the only chip that talks to the hardware
PPU · APU
the picture chip and the sound computer, each with private memory, reached only through registers
WRAM
128 KiB of console work RAM at $7E/$7F; its first 8 KiB also appears at $0000 in every system bank (the low mirror)
MMIO
hardware registers that look like addresses ($2100–$43FF); not memory
NMI · vblank
the interrupt fired when the beam finishes the picture; the only time video memory may be written
SA-1
a second 65816 in the cartridge, 10.74 MHz; cannot see WRAM or any register
BW-RAM
up to 256 KiB of cartridge RAM both CPUs see: the S-CPU through an 8 KiB window at $6000, the SA-1 linearly from bank $40
I-RAM
2 KiB inside the SA-1, shared; holds the mailbox and the frame token
D · DBR · M/X
direct-page base, data bank, and the 8/16-bit width flags — the three registers that make the same bytes mean different things
open bus
an address nothing answers: reads return leftovers, writes vanish silently

Glossary II — the pipeline

relocation · window mode
moving all of WRAM by one constant into BW-RAM so both CPUs can address it; no speedup by itself
coverage · evidence
which instructions executed (with proven widths), and where each one's data accesses landed
provenance
which ROM byte a stored value came from — how bank bytes travelling as data get rewritten
thunk · stub
a small generated routine: a thunk decides an ambiguous access at run time; a stub hands a call to the other CPU
offload · tree
a routine and everything it calls, copied to spare ROM and run verbatim on the SA-1
the split · tail · tok
the SA-1 runs the frame's logic in place; the S-CPU keeps the IO; the tok is the boundary that passes the token
token · done
two I-RAM cells; token advancing with done one behind proves the SA-1 runs every frame
surface · cover pair
a run the generator watched; a recording on an old build that donates coverage but cannot judge

a frame's first controller read: the instant two differently-lagged runs share
